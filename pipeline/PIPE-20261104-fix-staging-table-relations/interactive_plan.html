การเชื่อมต่อ Schema Staging: ผ่าน 100%
  • • Config.SUPABASE_SCHEMA = 'staging' ชี้ไปที่ staging ถูกต้อง
  • • Supabase อนุญาตการเรียก PostgREST สู่ Schema staging สำเร็จ
  • • ตารางเดี่ยวตอบกลับ HTTP 200 OK มีข้อมูลครบ:
    - system_settings: 200 OK
    - personnel (simple): 200 OK (พบรายชื่อบุคลากร)
    - user_accounts (simple): 200 OK (พบบัญชีผู้ใช้)
    - attendance_logs (simple): 200 OK (พบประวัติลงเวลา)
จุดที่เป็นปัญหา: ข้อจำกัดของ PostgreSQL LIKE
  • • คำสั่ง CREATE TABLE (LIKE ... INCLUDING ALL) ใน PostgreSQL ไม่คัดลอก Foreign Key Constraints ข้ามตาราง
  • • ทำให้ Schema staging ขาด Foreign Key เชื่อมระหว่าง: personnel ↔ user_accounts
    attendance_logs ↔ personnel
  • • เมื่อโค้ดเรียก Query แบบ Join ข้ามตาราง PostgREST จะส่งกลับ HTTP 400 (PGRST200: Could not find relationship) ส่งผลให้ฟังก์ชันคืนค่า [] หน้าจอจึงแสดง 0 คน

2. กลยุทธ์การแก้ไขแบบสมบูรณ์ 2 ชั้น (Double-Layer Bulletproof Fix)

1 ชั้นฐานข้อมูล (Database Schema Patch)

สร้างสคริปต์ SQL sql/fix_staging_foreign_keys.sql สำหรับรันใน Supabase SQL Editor:

  • เพิ่ม Foreign Key: staging.user_accounts(personnel_id) → staging.personnel(id)
  • เพิ่ม Foreign Key: staging.attendance_logs(personnel_id) → staging.personnel(id)
  • เพิ่ม Foreign Key: staging.attendance_logs(user_id) → staging.user_accounts(id)
  • รันคำสั่ง NOTIFY pgrst, 'reload schema'; เพื่อสั่ง PostgREST อัปเดต Cache ความสัมพันธ์ทันที
2 ชั้นโค้ดแอปพลิเคชัน (Client-side In-Memory Fallback)

ปรับปรุงโค้ดให้มีความทนทาน (Fault-Tolerant) ไม่ว่าฐานข้อมูลจะมีหรือไม่มี Foreign Key หน้าเว็บก็ไม่มีวันแสดงตารางว่างเปล่า:

  • PersonnelModel.getAll: หาก nested join ล้มเหลว จะสลับไปดึง personnel + user_accounts แยกกัน แล้วนำมาจับคู่ในหน่วยความจำ (In-Memory Stitching) ทันที
  • UserModel.getAll: หาก nested join ล้มเหลว จะดึง user_accounts + personnel แยกกัน แล้วจับคู่ client-side
  • AuthService.login / verify: เสริม fallback ดึงข้อมูลบุคลากรแยก หากความสัมพันธ์ PostgREST ขัดข้อง
  • AttendanceModel.getSpecialRequests: เสริม fallback ดึงข้อมูลคำขอพิเศษ
